# Authentication and domain authorization

This runbook is the source of truth for finance web authentication and
database-scoped authorization. Do not put passwords, one-time tokens, OAuth
secrets, Telegram secrets, or session cookies in this file.

## Account roles and domain groups

Authorization has two independent axes:

- The production operator account username is `admin`. Passwords and
  one-time tokens are never recorded in documentation.

- `role` is the account-wide capability ceiling:
  - `admin`: all permissions in every domain.
  - `viewer`: read permissions only, limited to assigned groups.
  - `guest`: the default for a new account. It has no permissions until an
    admin assigns one or more groups.
- `group` selects the database/domain the account may use:
  - `trading`
  - `english`
  - `affiliate`
  - `user`

Permissions use the stable form `<database>_<table>_<action>`, where `action`
is `read`, `insert`, `update`, or `delete`. Examples:

- `trading_klines_read`
- `trading_trades_insert`
- `english_english_daily_plans_update`
- `user_auth_account_groups_update`

The User database owns `auth_groups`, `auth_permissions`,
`auth_group_permissions`, and `auth_account_groups`. The
`auth_account_permissions` view resolves effective permissions. A new domain
table must add its four permission rows in a reviewed User migration.

Group assignment is replace-all and admin-only:

```http
PUT /api/v1/auth/accounts/{username}/groups
Content-Type: application/json
X-CSRF-Token: <value from csrf_token cookie>

{"groups":["english"]}
```

An empty `groups` array revokes all domain membership. The API validates every
group before deleting the previous membership, so an invalid group does not
partially update the account.

## One-time token login

The browser supports password login and one-time token login. It never accepts
a Google, Facebook, or Zalo access token pasted by a user.

1. Browser requests `POST /api/v1/auth/one-time-token/request` with a username.
2. The API always returns the same accepted response for existing and missing
   accounts to prevent username enumeration.
3. For an active account, the backend creates a cryptographically random token,
   stores only its bcrypt hash, and sends the plaintext token to the configured
   Telegram admin channel.
4. The token expires after 10 minutes and is atomically cleared on successful
   use, preventing replay and concurrent double-use.
5. Requests for the same account have a one-minute database cooldown. The HTTP
   endpoint also has a per-client rate limit.

All legacy static access-token hashes are cleared by the migration. Never log
the plaintext one-time token or return it in an HTTP response.

## Browser request security

- The session cookie is `HttpOnly`, `Secure` in production, host-only, and
  `SameSite=Lax`.
- Login also issues a readable, random `csrf_token` cookie. State-changing
  session routes require the same value in `X-CSRF-Token`.
- CORS uses an explicit origin allowlist. `*` is ignored and an Origin outside
  the list receives `403`.
- The runtime limits request bodies to 1 MiB, HTTP headers to 64 KiB, applies a
  global per-client token bucket, and applies stricter limits to login and
  one-time-token requests.
- These application controls reduce abuse and credential stuffing. Volumetric
  DDoS must still be absorbed at the edge/load-balancer because traffic that
  already reaches the Go process has consumed network capacity.

## Broker credential storage

Broker credentials are owned by the authenticated account and broker. The
browser may save, inspect masked status, rotate, or revoke credentials through
`/api/v1/broker/credentials`; it can never read the stored access key or secret
back.

The runtime encrypts each field with AES-256-GCM before writing it to the User
database. A random nonce is generated for every encryption and authenticated
additional data binds ciphertext to the account, broker, and field. Only the
internal broker adapter boundary may decrypt credentials when direct execution
is implemented. Direct broker execution remains disabled until then.

Production configuration belongs in `docker/env/production.env`, which is
copied into and sourced by the container at startup. The
`BROKER_CREDENTIAL_ENCRYPTION_KEY` exception is delivered from a
repository-scoped GitHub Secret to the runtime through CI/Coolify and must
never be committed or logged. Every Coolify service must attach to the external
`finance` network.

## Automated production trading verifier

The fixed username `tester` exists only to verify the deployed trading product.
On startup, when `PRODUCTION_TESTER_PASSWORD` is present, Finance MW upserts the
account, forces role `viewer`, removes every group except `trading`, and rotates
its bcrypt password hash. The password itself is generated by GitHub Actions,
masked in logs, and injected through the Coolify secret environment API; it is
not stored in this repository or this runbook.

The resulting authorization boundary follows the existing trading-viewer
contract:

- allowed: read-only trading routes such as strategy state, history, klines,
  runtime readiness, gRPC-backed trading metrics, and masked broker-key status;
- denied: broker-credential insert/update/delete, user administration, English,
  affiliate, and every other write permission;
- never exposed: decrypted broker credentials or stored password material.

`.github/workflows/verify-trading.yml` runs after a successful
main-branch Finance MW CI/CD delivery. It requires the immutable runtime image,
redeploys that exact SHA through Coolify with a newly generated verifier
credential, and fails if deployment does not complete within approximately ten
minutes. It then verifies, in one authenticated session:

1. login and `/api/v1/auth/me` report `tester`, `viewer`, and group `trading`;
2. `/api/v1/trading-metrics` returns a typed snapshot from the
   finance-live-action gRPC upstream;
3. masked broker-credential status remains readable, while a CSRF-valid
   credential mutation returns `403`;
4. `https://finance.thanhne.io.vn/trading` serves the official application.

The implementation and operating commands are documented in
`.agents/skills/production-trading-verification/SKILL.md`. Never convert this
verifier into an admin account or give it a write permission merely to make a
smoke test pass; that would invalidate the authorization evidence.
