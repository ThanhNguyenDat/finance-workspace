## Context

See `proposal.md` - Why. This replaces `add-quant-research-exec-command`'s
design for the same command (that change is `complete`, not yet archived);
this design supersedes its Decisions 1-5 rather than extending them.

Existing surface this builds on:

- `orchestrator.providers.codex.CodexProvider` and
  `orchestrator.providers.claude.ClaudeProvider`: both expose the same
  `BaseProvider.run_turn(prompt, *, cwd, timeout_seconds, on_event) ->
  ProviderResult(success, text, error)` shape, with their own account
  failover already handled internally. Both gain a small addition here
  (Decision 2): capturing and resuming the underlying SDK session/thread
  id, so a later stage doesn't have to re-explain everything to a fresh,
  memoryless turn.
- The underlying SDKs already support this: `openai_codex`'s
  `AsyncCodex.thread_resume(thread_id, ...)` continues an existing thread
  (confirmed present in the installed SDK); `claude_agent_sdk`'s
  `ClaudeAgentOptions.resume: str | None` loads a prior session by the
  `session_id` a `ResultMessage` already carries (also confirmed present
  and already read by `ClaudeProvider.stream()` today).
- `orchestrator.cli._shared`: `resolve_log_path`, `emit_event`/`emit_result`/
  `emit_error` (redacted stdout + JSONL), unchanged.
- `.agents/domain/quant-research-domain.md`: the non-negotiable invariants
  and classification/promotion rules both IMPLEMENT and VERIFY must read.
- Round 453 (this session) ran under the single-stage design and will finish
  under it; this design applies to rounds started after this change merges.

## Goals / Non-Goals

**Goals:**
- One `quant-research-exec` invocation runs an entire round's Codex+Claude
  cycle: implement, independent verify, bounded fix-and-reverify, finalize.
- Verify stays genuinely independent: it runs through `ClaudeProvider` (a
  different model/provider than the one that implemented), reading the same
  domain invariants, never Codex grading its own work.
- Every retry (fix, and the verify-question round-trip) is bounded — no
  path in this design can loop indefinitely.

**Non-Goals:**
- Automating the Claude PLAN stage (choosing the hypothesis, designing the
  test, backlog/web search when it's exhausted). That still happens in the
  operator's interactive Claude Code session before this command is ever
  invoked — this command's `PROMPT`/`--prompt-file` is that plan, supplied
  as input, not generated by this command.
- Automating the `PROMOTE` → `/opsx:propose` step. Unchanged from the prior
  design: Claude's own interactive session does this, since creating
  OpenSpec planning artifacts is Claude's job and a scripted turn has no
  slash-command/skill discovery to invoke it anyway.
- A generic multi-agent messaging framework. The Codex↔Claude round-trip
  added here (Decision 4) is one narrow, single-purpose, bounded exchange
  for this cycle only — not a reusable inter-agent protocol.
- Retrofitting round 453 or any round already running under the prior
  single-stage design.

## Decisions

**1. Stage sequence and state machine.**

```
IMPLEMENT (Codex)
   │  draft round file + CSV/index updates, do not commit
   ▼
VERIFY (Claude)  ──QUESTION──▶ ASK (Codex, one turn) ──▶ VERIFY continues (Claude, same pass)
   │
   ├─ PASS ────────────────────────────────────────────────────┐
   │                                                            │
   └─ FAIL (1st time) ──▶ FIX (Codex) ──▶ VERIFY again ─┬─ PASS ┤
                                                          │      │
                                                          └─ FAIL▼
                                                     (2nd time)  │
                                              CLOSE HONEST (Codex:
                                              NEEDS-MORE-RESEARCH
                                              or DATA-ISSUE, commit)
                                                                 │
                                                                 ▼
                                                    FINALIZE (Codex: commit)
```

Every box is one `CodexProvider.run_turn` or `ClaudeProvider.run_turn` call.
Boxes belonging to the same actor (IMPLEMENT→ASK→FIX→CLOSE-HONEST→FINALIZE
are all Codex; VERIFY's own continuation after ASK, and the post-fix
re-VERIFY, are both Claude) resume that actor's own session per Decision 2,
so each later call only needs to state its new instruction, not re-derive
context the actor already has. The Python orchestrator in
`quant_research_exec.py` drives this sequence directly (plain `if`/`while`
control flow over `await provider.run_turn(...)` calls) — no new concurrency
primitive, no background task; each stage still runs to completion before
the next starts, same as a human operator chaining CLI calls would, just
automated in one process.

**2. Capture and resume each actor's session/thread id across the cycle.**

`BaseProvider` gains an optional `resume_id: str | None` parameter threaded
through `start_turn(prompt, *, cwd, account, resume_id)` (default `None` —
`codex-exec`/`claude-exec`/existing tests are unaffected when they never
pass one), and a `last_session_id` property read after `collect_result()`:

- `CodexProvider.start_turn` calls `codex.thread_resume(resume_id, ...)`
  instead of `codex.thread_start(...)` when `resume_id` is given, and
  records the thread's id (from the `ThreadStartResponse`/`ThreadResumeResponse`)
  as `last_session_id` for the orchestrator to pass into the *next* Codex
  call in this cycle.
- `ClaudeProvider.start_turn` sets `ClaudeAgentOptions(resume=resume_id,
  ...)` when given, and `last_session_id` reads
  `self._result_message.session_id` after a turn (that field already
  exists and is already read for other purposes in `fakes.py`).

`quant_research_exec.py` keeps two local variables for the cycle's
lifetime, `codex_session_id` and `claude_session_id` (both start `None`),
updates them after every call to the matching provider, and passes them
into that provider's next call. This is the *only* reason `BaseProvider`
changes — account failover within one `run_turn` call is untouched; this
adds continuity *across* separate `run_turn` calls, a different axis.

Alternative considered: keep every stage a fresh, independent turn and have
the orchestrator re-paste full context (round plan, prior evidence, prior
questions/answers) into each prompt. Rejected once session resumption was
confirmed available in both SDKs — re-deriving context an actor already
has is strictly worse: slower, more expensive, and a fresh Codex turn
re-reading its own prior work from disk cannot recover *why* it made a
judgment call the way a resumed thread's own memory can.

**3. Verify's verdict is a structured marker line, not inferred prose.**

The VERIFY prompt instructs Claude to end its final message with exactly
one of:

```
VERIFY_RESULT: PASS
VERIFY_RESULT: FAIL <one-line issue summary>
VERIFY_RESULT: QUESTION <one question>
```

The orchestrator finds the last line matching `^VERIFY_RESULT: (PASS|FAIL|QUESTION)\b`
in the turn's result text. No match is a hard error (`emit_error`, exit
non-zero) — the orchestrator never guesses a verdict from unstructured
prose. `QUESTION` is only accepted on the *first* verify pass for a given
implement/fix output (Decision 4); a second `QUESTION` in the same pass is
treated as a parse error (the prompt tells Claude this explicitly, so this
should not occur in practice, but the orchestrator does not silently loop
if it does).

Alternative considered: parse free-form prose for approval/rejection
language. Rejected — exactly the kind of ambiguity this whole feature
exists to avoid; a structured marker is trivial for Claude to produce
reliably and trivial for Python to parse without heuristics.

**4. The verify→question→answer round-trip asks Codex, bounded to one
exchange.**

When VERIFY returns `QUESTION <text>`, the orchestrator:

1. Sends Codex one new turn: the domain rules plus "Answer this specific
   question about the round you just completed: `<text>`. Round file:
   `research/quant/rounds/round<N>-*.md` (draft). Metrics CSV:
   `research/quant/reports/optimize_loop_update_v2.csv`." — Codex is the
   party with full context of what it just did, so it is the natural one
   to answer a clarifying question about its own work, the same way a code
   author answers a reviewer's question.
2. Sends Claude one more turn: the original VERIFY prompt and evidence,
   plus "Your question: `<text>`\nCodex's answer: `<answer>`\n\nDecide now
   — you may not ask another question this pass; end with `VERIFY_RESULT:
   PASS` or `VERIFY_RESULT: FAIL <issue>`."

This costs at most one extra Codex turn and one extra Claude turn per
verify pass (implement's verify pass and, if it happens, the post-fix
verify pass each get their own independent one-question allowance — not a
cycle-wide budget of one, a per-pass budget of one).

Alternative considered (raised explicitly as an option): spawn a fresh
Claude sub-agent review turn instead of asking Codex. Rejected as the
default — it would need the full round context re-supplied from scratch
(duplicating most of what the original VERIFY turn already has) to answer
what is usually a question about *why Codex did something*, which Codex
already knows and a fresh reviewer would not. Asking Codex directly is
cheaper and more likely to actually resolve the question. Not ruled out
for a future round of design if a concrete case shows Codex's self-report
is the wrong source for a particular kind of question — just not built now.

**5. Fix is bounded to exactly one attempt per verify failure chain.**

`FAIL` on the *first* verify pass (against IMPLEMENT's output) triggers one
Codex FIX turn (given the `FAIL` issue text as its brief) and one more
VERIFY pass. `FAIL` on *that* second pass does not trigger a second FIX —
the orchestrator instead sends Codex a CLOSE-HONEST turn: "Verify still
found a problem after one fix attempt (`<issue>`). Close this round
honestly: reclassify as `NEEDS-MORE-RESEARCH` or `DATA-ISSUE` (whichever
fits) rather than fixing again, per the domain rules' round-split
guidance, then commit." This matches the already-documented "fix at most
once, then close honest" rule in `.claude/commands/quant/research.md` and
`.agents/skills/quant-research-loop/SKILL.md` — this design automates that
existing rule, it does not invent a new one.

**6. `--role` is removed; `--round` keeps its auto-detect behavior.**

```
quant-research-exec [PROMPT] [--prompt-file FILE] [--round N]
                     [--cwd DIR] [--timeout-seconds N]
```

There is only one entry point now (a full cycle), so a stage-selector flag
no longer has a role to select between. `--round` is still optional
(auto-detects the next round the same way as before); still the only value
`--change quant-research-round-<N>` is derived from.

`--model`/`--effort` are dropped from this command's surface (present on
`codex-exec`/`claude-exec` today). With two different providers/model
families now involved in one invocation, a single generic override no
longer has an unambiguous target, and no real round this session has
needed either flag. `codex-exec`/`claude-exec` remain available directly
for anyone who needs to override a specific provider's model for a one-off
turn outside this cycle.

**7. One `--timeout-seconds` value applies per stage, not to the whole
cycle, with a much larger default than `codex-exec`'s.**

Each stage (implement, verify, ask, fix, close-honest, finalize) gets its
own independent `timeout_seconds` budget — a slow verify pass does not
eat into implement's budget or vice versa. Default changes from the
generic `DEFAULT_TIMEOUT_SECONDS` (300s, sized for a quick one-off turn) to
a quant-research-specific default of 3600s (round 452's real implement
turn took ~20 minutes; a default that is routinely too short is worse than
one that is generously large and rarely hit) — still overridable via
`--timeout-seconds` for a shorter smoke test.

**8. Logging: one log file per round, a `stage` field on every line.**

Still `tools/orchestrator/logs/quant-research-round-<N>/quant-research-exec.log`
(unchanged path convention), but every emitted JSONL line now includes
`"stage": "implement" | "verify" | "ask" | "fix" | "close_honest" |
"finalize"` so a reader (or the "simple web UI to stream these logs" the
operator mentioned wanting later) can reconstruct which part of the cycle
produced which event without guessing from content.

## Risks / Trade-offs

- [A resumed thread/session accumulates a long conversation across
  implement→ask→fix→close-honest→finalize, risking context-window bloat or
  the SDK's own compaction changing behavior mid-cycle] → Bounded by
  Decisions 4-5 already keeping the *number* of resumed turns small (at
  most implement + ask + fix + close-honest + finalize = 5 for Codex, at
  most 2-3 for Claude); each individual prompt still stays focused on its
  own instruction rather than re-pasting history, so the accumulated
  session grows with turns taken, not with prompt verbosity.
- [`thread_resume`/`resume=` fails (stale id, backend error) mid-cycle] →
  Surfaces as that stage's own `ProviderResult(success=False, ...)`, same
  as any other turn failure; the orchestrator aborts the cycle with an
  error rather than silently starting a fresh, memory-less turn in its
  place (a silent fallback would defeat Decision 2's purpose without
  telling anyone).
- [Claude's VERIFY turn fails to produce a parseable `VERIFY_RESULT:` line]
  → Hard error, exit non-zero, nothing committed. Safer than guessing a
  verdict; the operator re-runs once the prompt or Claude's behavior is
  understood.
- [Asking Codex to answer its own question could get a self-serving answer
  that doesn't actually resolve a legitimate concern] → Not fully solvable
  without a second independent party (rejected in Decision 4 as
  disproportionate for now); mitigated by the one-question cap and by
  Claude's re-verify still being free to answer `FAIL` even after getting
  an answer — asking a question does not obligate Claude to accept it.
- [A stage's own Codex/Claude account failover already retries internally;
  combined with this cycle's own fix/question retries, a single invocation
  could now run many minutes to hours end to end] → Expected and accepted
  for a research round (matches real round durations observed this
  session); the per-stage timeout (Decision 7) still bounds each individual
  stage, and the fix/question bounds (Decisions 4-5) bound the cycle's
  shape.
- [`.claude/commands/quant/research.md`'s Bước 3-8 describe the old
  hand-chained flow] → Out of scope for this change's own tasks (see
  proposal.md - Impact); a follow-up doc update once this lands, tracked
  as its own task below so it isn't forgotten, not silently left stale.

## Migration Plan

`quant-research-exec`'s CLI surface changes (removes `--role`, `--model`,
`--effort`; changes default timeout) — a breaking change to that one
command's flags, not to `codex-exec`/`claude-exec`/`claude_exec`/anything
else. No round is currently relying on the old flags outside this session's
own manual testing. Update `.claude/commands/quant/research.md` in the same
change so the documented usage never drifts from the implemented behavior.
